# 代码审查

你拿到的是一次代码变更审查任务。先自己把变更内容找出来——不要向用户提问，也不要请求确认，直接动手。

## 步骤

1. **确定审查范围**——按以下顺序取，取到哪个用哪个：
   - 暂存区与工作区的改动：`git diff` 与 `git diff --staged`
   - 若工作区干净，取最近一次提交：`git log -1` 加 `git diff HEAD~1`
   - 若用户指明了文件或目录，就只看那些路径
2. **读全上下文再下结论**——不要只看 diff 的一小段就评论。改动涉及的函数/类改动前是什么样、被谁调用，都要读一遍再判断。
3. **逐项排查**，优先级从高到低：
   - **正确性**：边界条件、空值、off-by-one、异常路径、并发下的竞态；某个分支是否永远走不到
   - **错误处理**：异常是否被吞掉、失败是否上报、超时与重试是否合理
   - **资源与性能**：连接/文件句柄是否释放、循环里是否有重复的重活、是否有不必要的 O(n²)
   - **安全**：路径拼接、命令拼接、凭据硬编码、反序列化不可信输入
   - **可维护性**：命名是否达意、是否有重复逻辑、注释是否与代码脱节
4. **过滤噪声**——只报你能说清「什么问题、什么条件下会出错」的项。风格偏好、格式问题、纯主观的重构建议不要报。

## 输出格式

按严重程度分组，每组内按文件路径排序：

**必须修复**（会导致错误结果、崩溃或安全问题）
- `路径:行号` — 问题是什么；什么输入/条件下会出错；怎么改

**建议修复**（不会立刻出错，但会成为隐患）
- `路径:行号` — 同上

**已核查无问题**
- 一句话列出你重点看过、确认没问题的方面

若确实没有发现必须修复项，就直说，不要为了凑数编造问题。

## 注意

- 每条结论都要能指到具体文件与行号
- 不确定的地方明说「不确定」，不要用肯定的语气掩盖猜测
- 不要修改任何文件——只审查，不动手
