# 生成一次提交

按下面的顺序走完，不要跳步，也不要在没看过变更内容的情况下就动手提交。

## 步骤

1. **看清当前状态**——并行执行这三条，不要串行等：
   - `git status`：有哪些新增、修改、删除
   - `git diff`：未暂存的改动内容
   - `git diff --staged`：已暂存的改动内容
2. **读懂变更意图**——把 diff 看完再说话。变更属于哪种类型：新功能、缺陷修复、重构、文档、测试、还是构建配置？这决定提交信息的措辞。
3. **确认变更范围合理**——如果发现改动横跨多个不相关的主题，先向用户说明并询问是否拆分提交，不要擅自替用户决定。
4. **检查敏感内容**——扫一遍即将提交的内容，确认没有密钥、令牌、`.env`、本地绝对路径、调试用的临时打印。
5. **暂存**——只暂存本次提交该包含的文件，用具体路径而不是 `git add -A`，避免把无关改动一起带上。
6. **写提交信息**——遵循以下规范：
   - 首行是一个简短祈使句（动词开头），长度控制在 50 字符内，结尾不加句号
   - 首行与正文之间空一行
   - 正文说明「为什么这么改」而不是「改了什么」——改动内容 diff 里已经写着了
   - 项目内已有提交信息的语言和风格优先于本条规范
7. **提交**——用 heredoc 传多行提交信息：`git commit -F - <<'MSG'`，避免转义问题。
8. **核实结果**——`git log -1 --stat` 确认提交内容与预期一致。

## 注意

- 不要用 `--no-verify` 跳过钩子；钩子失败要看清原因并修复
- 不要 `git push`，除非用户明确要求
- 不要把 `git add -A` 当成默认选项
